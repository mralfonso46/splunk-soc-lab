# INC-001 — SSH Failed Authentication

**Title:** SSH Failed Authentication / Brute-Force-Like Activity  
**Severity:** Medium  
**Status:** Closed  
**Source:** Kali Linux (`10.10.10.2`)  
**Destination:** Ubuntu Splunk VM (`10.10.10.1`, host `ubuntu-server`)  
**Detection:** SOC - SSH Failed Authentication Threshold

## Summary
A controlled series of failed SSH authentication attempts was generated from Kali against the Ubuntu server. Splunk ingested the events from `/var/log/auth.log` and detected a threshold of failed authentication activity.

## Technical Evidence
- Source IP: `10.10.10.2`
- Target host: `ubuntu-server`
- Username observed: `invaliduser`
- Relevant messages: `Invalid user` and `Failed password`
- One investigation result showed 8 matching events; a later threshold search showed 16 events in the selected window.
- No successful SSH login was observed in the investigated `Accepted` search.

## Timeline
- Controlled failed SSH attempts generated from Kali.
- Events ingested into `soc_lab`.
- Threshold search returned `ubuntu-server` with a qualifying count.
- Scheduled alert triggered and results were reviewed.

## Indicators
- `10.10.10.2`
- `invaliduser`
- SSH authentication failures

## Analysis
The evidence shows repeated failed SSH authentication attempts from the Kali lab host. Because the activity was intentionally generated for testing, it is treated as a controlled security test rather than a real compromise.

## Impact
No successful SSH authentication was observed in the investigated data.

## Containment Recommendation
In a production environment, validate the source, review surrounding authentication activity, and consider rate limiting or restricting SSH access if the source is unauthorized. No blocking action was required in this lab.

## Lessons Learned
- Centralized authentication logs support rapid triage.
- A simple threshold rule can identify repeated failed authentication.
- Alert results should be validated against raw events before incident closure.
