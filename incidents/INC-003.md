# INC-003 — Network Port Scan

**Title:** Network Port Scan  
**Severity:** Medium  
**Status:** Closed  
**Source:** Kali Linux (`10.10.10.2`)  
**Destination:** Ubuntu Server (`10.10.10.1`)  
**Detection:** SOC - Possible Port Scan

## Summary
A controlled Nmap TCP connect scan of ports 1–1000 was performed from Kali against the Ubuntu server. TCP SYN telemetry was captured on the Ubuntu lab interface and written to `/var/log/portscan.log`, then ingested by Splunk.

## Technical Evidence
- Source IP: `10.10.10.2`
- Destination IP: `10.10.10.1`
- Interface: `ens38`
- Capture filter: TCP SYN packets
- Initial ingestion result: `1,003` events
- Example destination ports observed included 423, 167, 989, 151, 434, 944, 682, 743, and 994.
- Alert: `SOC - Possible Port Scan`

## Timeline
- TCP SYN capture started on `ens38`.
- Nmap `-sT -p 1-1000` executed from Kali.
- TCP SYN events were written to `/var/log/portscan.log`.
- Splunk indexed the telemetry under `soc_lab`.
- Detection threshold was met.
- Scheduled alert triggered.

## Indicators
- Source: `10.10.10.2`
- Target: `10.10.10.1`
- TCP SYN activity across many destination ports
- Nmap TCP connect scan

## Analysis
The telemetry shows a high volume of TCP SYN attempts from the Kali host to many ports on the Ubuntu server. This pattern is consistent with the controlled port-scan test performed in the lab.

## Impact
No production impact. The scan targeted the isolated lab server.

## Containment Recommendation
In production, validate whether the source is authorized, correlate with asset ownership and change records, and investigate the destination service exposure. Network controls can be applied when unauthorized scanning is confirmed.

## Lessons Learned
- Network telemetry is required for network detections; auth logs alone do not reliably show port scans.
- A temporary tcpdump-to-log workflow can provide lightweight lab telemetry.
- Threshold-based SPL can detect high-volume SYN activity without complex field extraction.
